## Spike A — dynamic TSX import with embedded-module resolution

**Question.** Can a `bun build --compile` binary, at runtime on Windows, dynamically
import an arbitrary external `.tsx` from disk and have *that file's*
`import { … } from '@termcraft/runtime'` resolve to a module embedded in the binary —
with no `node_modules` and no `package.json` anywhere near the `.tsx`?

**Verdict: `YES-WITH-FALLBACK: a`** — a `Bun.plugin` runtime resolver, registered before
the dynamic import.

**Evidence.** The naive path fails exactly as the plan's research predicted:
`ResolveMessage: Cannot find module '@termcraft/runtime'`, reproduced in a second
location with no `package.json` ancestor to rule out a placement artifact. `Bun.plugin`
*is* honored inside a compiled binary; the result was verified non-stub, because the
rendered string exists whole in no source file and can only be produced by executing the
embedded module against the external page's props.

**The fallback choice is not a cost tiebreak.** All four candidates pass a toy page, but
**only (a) survives a page importing a relative sibling.** (b), (c) and (d) all fix the
bare specifier by relocating the page into a scratch directory, which breaks every other
relative path and silently redirects `import.meta`/`__dirname`. Real pages have siblings.
(a) is the only approach that leaves the page where the author put it.

**Consequences for implementation:**

1. **The host registers three specifiers, not one:** `@termcraft/runtime`,
   `react/jsx-runtime`, and `react/jsx-dev-runtime`. Registering only the first fails a
   real JSX page with `Cannot find module 'react/jsx-dev-runtime'` — the transform's
   generated helper import must resolve too.
2. **Resolution fails open, not closed.** Because the host must register
   `react/jsx-runtime` unconditionally, a page that reached the runtime with an explicit
   helper import would *run* rather than fail at load. The Gate's source-text scan
   (§3.1) is therefore load-bearing and has no second line of defense underneath it.
   This is a defense-in-depth gap, not a broken spec claim — see the amendments table.
3. **Respawn-per-source is a correctness requirement, not a preference.** Bun's module
   cache is stale and `?v=` cache-busting does not work: `queryReturnsSameModuleObject:
   true` isolates the mechanism — Bun ignores the query as a module key. A
   directory-listing cache compounds it: a file created in an already-resolved directory
   is invisible. Respawn cures both; nothing else tried does.
4. **The preview budget is spawn, not import.** One preview is one process spawn:
   **44–52 ms**, of which import and render are **~1 ms**. Spawn dominates by ~50×. Treat
   45 ms as a **floor** — it was measured on a minimal 94 MB probe, and the real host
   additionally carries OpenTUI's native core. The robust claim is the *ratio*, not the
   absolute number.

**The JSX facade contract `@termcraft/runtime` must implement** — every item below was
observed, not inferred from React's documentation:

- `key` is **positional** — the third argument, absent from `props`. A `(type, props)`
  helper silently drops every key. Invisible with a string stand-in; a correctness bug in
  a reconciling runtime.
- `jsx` and `jsxs` share one signature `(type, props, key)`; children live in
  `props.children` for both. `jsxs` only signals that the children array is static.
- **`jsxs` is production-only.** Dev emits `jsxDEV` for everything, single- and
  multi-child alike, distinguishing shape via `isStaticChildren`.
- `Fragment` is never a helper — it arrives as the `type` argument and must be an
  exported *value*.
- The `jsx`/`jsxs` split is by **child slots written in source**, not runtime
  array-ness: a root with one source slot holding a 2-element array routes to `jsx`.

**A trap the host must not fall into.** `process.env.NODE_ENV` read via dot access is
**inlined at build time** as the literal `"development"` and lies forever, while the
transform follows the real environment variable. `Bun.env.NODE_ENV` returns the truth.
A host that branches on the inlined value registers the dev helper and then fails under
production from a variable it cannot see. Registering both subpaths unconditionally is
the pragmatic answer.

## Spike B — styled cell-frame capture from the headless renderer

**Question.** Can OpenTUI render headlessly at a fixed size with no TTY, from inside a
`bun build --compile` binary on Windows, and yield per-cell char + fg + bg + attributes
as §4.2's host protocol requires?

**Verdict: `YES`.**

**Known Risk #2 resolves positive, and this is the best news in the set.** The plan
feared OpenTUI's native Zig core would not survive `--compile`, calling it "a known hard
spot". It does survive, because upstream already solved it: the win32 binding's own
source reads `import("./opentui.dll", { with: { type: "file" } })` — Bun's asset
embedding. `--compile` embeds the DLL (14 embedded files) and FFI loads it from the
binary rather than looking beside the executable. Proven by running the single-file
`.exe` in a directory containing only itself, with a verbatim listing showing `*.dll: 0`,
`*.node: 0`, `node_modules present: False`. No workaround needed.

**Losslessness, scoped precisely.** A full 80×24 grid reconstructs losslessly from
`captureSpans()` for **char + fg + bg + the 8 text attributes** — §4.2's tuple. Measured,
not argued: a per-cell oracle compared every cell's style against
`currentRenderBuffer.buffers` — **1920 cells, 0 mismatches**. Note the oracle is the
spans' **pre-image**, not an independent witness (`getSpanLines()` is implemented on top
of `.buffers` and shares the same `RGBA.fromArray` call), so this is a round-trip test: a
systematic decoder error would cancel on both sides. It is still the right test — it
catches column misassignment in the wide-character expansion, which is the real risk.

**`captureSpans()` is lossy for hyperlinks.** `attributesWithLink(BOLD, 7)` = `0x701`
does not round-trip, because spans mask `& 255` and drop the link id. This does not move
the verdict — §4.2 names the 8 text attributes, the brief scoped the question to
bold/dim/italic/underline/reverse, and the package itself draws the same line
(`types.d.ts:21-23`: *"Currently we only use the first 8 bits for standard text
attributes"*). The loss is recoverable through `buffers.attributes` + `getLinkId()`.

**Consequences for implementation:**

1. **`captureSpans()` returns runs, not per-cell records** —
   `{cols, rows, cursor, lines: [{spans: [{text, fg: RGBA, bg: RGBA, attributes, width}]}]}`.
   `fg`/`bg` are `RGBA` class instances carrying `intent`/`slot`, so palette indices
   survive as indices.
2. **Take style from `.buffers`, take text from `getSpanLines()`. Never text from
   `buffers.char`.** For ASCII `char` is a codepoint, but wide characters carry a
   continuation sentinel (`日` → `0x900200fd`), and reading it as a codepoint throws
   `RangeError`. OpenTUI's own `getSpanLines()` refuses to read text from `char[]` for
   exactly this reason — it uses `getRealCharBytes(true)` and treats `char[i]` only as a
   continuation flag.
3. **`span.width` is display width, not codepoint count.** `日本語ab` is 5 codepoints and
   width 8. This is the single place §4.2's protocol can silently corrupt a frame.
4. **Build the production host on the public API (Option A), not `@opentui/core/testing`.**
   `createTestRenderer` is a testing-scoped export of a pre-1.0 package carrying a
   production requirement — a real architectural exposure. The public rebuild is clean:
   `intermediateRender()` is public and paints; `createCliRenderer` works with fake
   streams; and backpressure is **moot** rather than dropped, because with
   `bufferedOutput: "memory"` no feed is allocated at all — the testing harness's own
   `_feed?.isBackpressured()` is a no-op there, and `createTestRenderer` defaults to
   memory mode. The rebuild loses nothing the harness was doing.
5. **Two traps in that recipe.** `createCliRenderer` sizes as
   `stdout.columns || config.width || 80` — a fake stream's `columns` **overrides**
   `width`, so rendering "at the preview's size" can silently render the wrong size. And
   `setupTerminal()` puts stdin in raw mode, so the shim needs `setRawMode`.
6. **Export is seconds, not minutes.** Median ~2.2 ms per fresh 80×24 host compiled;
   worst observed 15.40 ms × 500 renders ≈ 7.7 s.

## Spike C — TypeScript check inside the compiled binary

**Question.** Can the TypeScript compiler type-check an external `page.tsx` from inside a
`bun build --compile` binary on Windows, with the lib `.d.ts` files and
`@termcraft/runtime`'s types embedded — and fast enough to sit inside a turn?

**Verdict: `YES-WITH-FALLBACK`. Latency: 337 ms cold** (median of 4, range 253–503),
**~170 ms warm**, ~2–4 ms per retry with the compiler held open, ≈35 ms for a held-open
turn.

**The plan's design for this spike did not survive contact with reality.**
`bun add typescript` resolves to **7.0.2 — the native Go port**. `ts.createProgram`,
`ts.JsxEmit` and `CompilerHost` **do not exist** there: the package's main export is
`{version, versionMajorMinor}` and nothing else, and `node_modules/typescript/lib` holds
five files, none of them a `lib.*.d.ts`. The libs and the compiler ship in a
**per-platform** package (`@typescript/typescript-win32-x64`). The probe was rebuilt on
`typescript/unstable/sync` over a virtual filesystem (`new API({ fs })`), which is TS7's
CompilerHost analogue.

**Why "with fallback".** Two independent facts, both measured:

- `uv_spawn` cannot execute a `B:/~BUN/root/…` path — the OS loader knows nothing about
  Bun's embedded-file namespace, so the compiler cannot be launched from inside the
  binary.
- `tsgo` ships as a **`noembed`** build: its libs are not compiled into the Go binary, and
  it panics at startup if `lib.d.ts` is not beside the executable.

So the binary extracts the 24.5 MB `tsc.exe` **and all 88 lib files** to disk once
(57 ms) and spawns it from there. `@termcraft/runtime`'s types and the synthesized
tsconfig are what the virtual filesystem is genuinely for — the libs are served from disk,
and the VFS branch for them is redundant.

**The Gate hole, proven rather than argued.** The natural diagnostic union — per-file
plus program diagnostics — **omits `getGlobalDiagnostics()`**, and that is where
missing-lib errors surface. Deliberately breaking `lib.es5.d.ts` produced four
`2318 Cannot find global type 'Object'/'Boolean'/…` diagnostics, **all in the `global`
bucket and zero anywhere else**. A Gate built on the natural union would have returned
`[]` — clean — for a program with no `Object` type at all. The union also
**double-reports** (code 6053 lands in both `program` and `global`), so the Gate must
dedupe on `(code, fileName, pos)`.

**A finding that constrains how the Gate can ever be tested.** A broken lib link is
**silent unless the page happens to use that lib** — breaking `es2015.iterable` against a
page using `new Map()` still returns `[]`. No fixture can therefore prove chain
completeness. The only evidence that can is the cross-check, which now reports both
directions:

```json
{"distinctLibsAsked":87,"embeddedLibCount":88,
 "askedButNotEmbedded":[],"embeddedButNeverAsked":["lib.d.ts"]}
```

`askedButNotEmbedded: []` is the completeness proof. `embeddedButNeverAsked:
["lib.d.ts"]` confirms the sentinel story from the other side — it is the one embedded
file the compiler stats but never reads.

**Consequences for implementation:**

1. **Per-platform builds.** The lib import path is pinned to `@typescript/typescript-win32-x64`.
   Shipping Linux and macOS means N builds, each with its own codegen step targeting that
   platform's package. Microsoft publishes all twenty platform packages, so the mechanism
   exists; the build system has to be built for it.
2. **Extract to a stable per-user directory, not `%TEMP%`.** The probe used `%TEMP%`
   because its brief said so. For the product this is the wrong choice: `%TEMP%` is
   swept, and it is the highest-signal location for the dropper heuristics discussed
   below. `%LOCALAPPDATA%\termcraft\tsc-<version>\` is where per-user applications
   legitimately live, survives cleanup, and is permitted by AppLocker policies that
   forbid `%TEMP%`.
3. **Pin the TypeScript version exactly.** The Gate is built on
   `typescript/unstable/sync` — a subpath whose name is a stability warning — and the
   88-file lib chain and platform-package layout are both version-specific.
4. **The Gate must distinguish "the compiler crashed" from "the page is clean."** The
   probe does not fall into this trap (no `try`/`catch` around the check, so a spawn
   failure exits non-zero rather than printing `[]`), but product code must guard it
   deliberately. An unguarded Gate reads a crash as success — the exact failure the wall
   exists to prevent.
5. **`lib: ["esnext"]` is load-bearing.** Without the pin, `lib.esnext.full.d.ts` pulls in
   DOM and friends: 2,361,763 bytes (~2.25 MiB) of `.d.ts` the product never needs.

**Antivirus, stated at exactly the strength it was measured.** Writing a 24.5 MB
unsigned executable to disk and immediately spawning it is the textbook behavioral
signature of a dropper, and that is why this is a risk at all. What was measured: the
first execution of a freshly written exe costs **~2–3×** (cold `checkMs` 114–168 vs warm
47–71), decaying after one run. What was **not** established: that antivirus is the
cause — a cold file cache and paging in a fresh 24.5 MB image predict the same shape, and
the discriminating experiment (one run with a `%TEMP%` exclusion configured) was not run.
What was **not measured at all**: reputation blocking, and quarantine — the genuine tail
risk, where the Gate does not slow down but stops existing.

## Amendments required before implementation planning

No spike returned `NO`, so no spec claim is invalidated outright. Eight need editing.

| # | Spec claim | Status | Required amendment |
| --- | --- | --- | --- |
| 1 | §4.1 — single self-contained binary | **Partially false** | Holds for OpenTUI's native core (upstream already embeds `opentui.dll`). Fails for TypeScript: a 24.5 MB compiler plus 88 lib files reach disk at first run and are spawned as a subprocess. The spec must say so. |
| 2 | §4.1 — toolchain versions | **Underspecified** | Pin the TypeScript major. TS7 is the Go port; TS5's JS API does not exist there and the spike's entire design is void on it. |
| 3 | §4.1 — one build | **False for the compiler** | Per-platform builds are mandatory: the lib import path is platform-pinned. |
| 4 | §4.2 — Gate accepts only what validated | **Hole found** | The Gate must union `getGlobalDiagnostics()` and dedupe on `(code, fileName, pos)`. Without the union it returns clean for a program with no `Object` type. |
| 5 | §4.2 — respawn per source | **Understated** | Promote from architectural preference to **correctness requirement**. Bun's module cache is stale and cannot be busted by query. |
| 6 | §3.1 / §11.1 — explicit `react/jsx-runtime` must fail | **Stands, but unbacked** | The claim is satisfiable and enforcement already lives at the Gate's source-text scan (§3.1), the relink rescan, and the declaration environment — not the resolver. But resolution **fails open**, so that scan has no backstop. Record it as a defense-in-depth gap. |
| 7 | §4.2 — "styled cell frames (char + fg + bg + attributes)" | **Scope needed** | Lossless for char + fg + bg + the 8 text attributes. Hyperlink ids are dropped by spans; recover via `buffers.attributes` + `getLinkId()`. Text must come from `getSpanLines()`, never `buffers.char`. |
| 8 | §5.8 / runtime API — the facade's JSX surface | **Contract discovered** | `key` is positional; `jsx`/`jsxs` share `(type, props, key)` with children in `props.children`; `jsxs` is production-only; `Fragment` is an exported value passed as `type`. The host registers three specifiers. |

Two further facts belong in the spec even though they contradict nothing:

- **Preview cost is spawn** (~45–52 ms floor), not import (~1 ms). Any preview design that
  optimizes import is optimizing 2% of the budget.
- **`@opentui/core/testing` is not the production path.** Build on the public API; the
  rebuild loses nothing, and `/testing` is a testing-scoped export of a pre-1.0 package.

## What remains unmeasured

Stated plainly, because the spikes' value is knowing where the edge is:

1. **TypeScript 5 was never probed.** The choice of TS7 is a choice between one measured
   option and one unmeasured one — made deliberately, on the reasoning that TS7 is where
   TypeScript is going and that its costs are known rather than guessed. If per-platform
   builds or the extraction step later prove intolerable, TS5 is the unexplored escape
   hatch and re-opening it means a real probe, not an assumption.
2. **Antivirus quarantine and reputation blocking.** Only the first-execution slowdown was
   measured, and its cause was not isolated.
3. **`@opentui/react`, and both agent SDKs**, are pinned from a lockfile but exercised by
   no probe. Nothing is known about their behavior inside a compiled binary.
4. **The interactive renderer.** Only the headless capture path was compiled. §3.5 defers
   interactive mode to v1.0, so this is on schedule, not overdue.
5. **The real host's spawn cost.** 44–52 ms is a floor measured without OpenTUI's native
   core aboard.
6. **Cross-platform anything.** Every probe was built and run on Windows 11 only, per the
   plan's constraint. macOS and Linux are unknown.
